# ADR-0014: End-to-end tests of the native app with Maestro

- Status: Accepted
- Date: 2026-11-23
- Decided by: owner (asked for automated app tests "like Playwright" instead of clicking through the simulator; accepted Maestro, a review account for the tests, and nightly runs on macOS runners)
- Amended: 2026-11-23, owner (option "1a"): a test build with a fake microphone and an intercepted transcription request, so the recording flow runs in CI without paid calls

## Context
Playwright covers the web client in desktop and mobile browser engines (`e2e-browsers.yml`), but not the native shells: the iOS and Android apps add native permission prompts, the sign-in deep link and their own layout. The first manual iOS check found a real defect (the production backend did not yet accept `platform: "ios"`), and manual clicking in the simulator does not scale.

## Decision
- **Maestro** drives the installed app on an iOS simulator through flows in `frontend/maestro/` (YAML). It sees both native iOS views and the WebView content, so one flow covers a native prompt and the web interface. It is a test tool on the developer machine and the CI runner only; nothing ships with the app.
- `scripts/test-app.sh ios` runs the flows; `scripts/build-ios.sh sim` builds an unsigned simulator app into `artifacts/`; `just e2e-ios` does both.
- The flows sign in with a **review account** (a normal Supabase user created by `scripts/create-review-account.sh`) against the production backend. Its password is generated and never printed; it lives in the owner's Keychain and in the repository secret `REVIEW_LOGIN_PASSWORD`; the address is the secret `REVIEW_LOGIN_EMAIL`. The same account serves app-store reviewers through "Вход для проверки".
- The flows stop before anything that calls a paid AI provider: they type no answers and never press the answer-check button, and the simulator app is a test build that sends no recording for transcription (next point). C-14 now lists the routes these flows must not reach; nothing enforces it except review, because production has the provider keys.
- **Test build.** `scripts/build-ios.sh sim` builds the web app with `VITE_TEST_AUDIO=true`. In that build `VoiceRecorder.start()` takes its stream from a bundled audio file instead of `getUserMedia` (`frontend/src/testBuild/fakeMicrophone.ts`: the file is inlined into that chunk as a data URL, so no request is made, then decoded and played in a loop through an `AudioContext` into a `MediaStreamAudioDestinationNode`), and `transcribeAudio()` does not call `POST /api/transcriptions`: `frontend/src/testBuild/fakeTranscription.ts` checks the recording (an audio MIME type, at least 1000 bytes) and returns the response shape of that route with the canned transcript "Merhaba, hesap açmak istiyorum.", or throws, so the interface shows the transcription error. No other request is intercepted. The fixture `frontend/src/testBuild/phrase.m4a` (about 15 KB of AAC, 2.6 seconds) was generated offline with the macOS voice "Yelda" (`say` and `afconvert`), not with an AI service. Both modules are loaded with a dynamic `import()` behind the flag, so other builds leave them and the fixture out. The flag is accepted only from the process environment: `vite.config.ts` (`frontend/build/testAudioFlag.ts`) refuses it from an env file such as `.env.local`, because the scripts can clear only the environment, and refuses it outside the native-app mode and on Vercel. `sync` and `open` clear it in the environment, and `sim` restores the normal web build in `frontend/ios` when it finishes; `scripts/build-android.sh` clears it. `frontend/build/checkNoTestAudio.mjs` fails on the fixture or a test-module marker; it runs in `just frontend-build` on a web build and a native-app build made without the flag, on `frontend/ios/App/App/public` after `sync`, `open` and the `sim` restore, and on the web build in `scripts/build-android.sh` and `scripts/build-android-play-aab.ps1` before Gradle.
- **Only on a verified test build.** `microphone.yaml` is tagged `needs-test-build`, because on any other build its finished recording would go to production `/transcriptions` (C-14). `scripts/test-app.sh` runs flows with that tag only on iOS and only after finding the marker `turktalk-test-audio-build` in the `App.app` it installs (`scripts/lib/test-audio-build.sh`). With no simulator build to inspect (an app already installed, for example from Xcode), a build without the marker, or on Android, it skips them with a message and runs the other flows. Maestro applies `--exclude-tags` only to a folder, not to flow files named on its command line, so the runner lists the flow files and drops tagged ones itself.
- **Feedback dictation is not covered.** The test build replaces the recorder for every caller, but only the practice transcription (`transcribeAudio`) is answered on the device; feedback dictation in Settings would still send its recording to `/feedback/transcribe`, which calls a provider. No flow may use it (C-14).
- Unsigned simulator builds for these tests are an exception to C-24; store builds still need the owner's instruction.
- CI: `.github/workflows/app-e2e.yml` runs nightly and on demand on the owner's own Mac, a self-hosted runner with the label `turktalk-mac` (amended 2026-11-23 at the owner's request; it first used GitHub's `macos-15` runner, whose minutes cost about ten times Linux minutes). Pull requests do not run it. Because the repository is public, the runner may only be used by jobs that run code already on `main`: the workflow has only `schedule` and `workflow_dispatch` triggers and a `github.ref == 'refs/heads/main'` condition, and no workflow with a `pull_request` trigger may use that label. Runners have no audio input; the test build does not need one, so `microphone.yaml` runs there too (the workflow builds a fresh test app before the flows).

## Alternatives considered
- **Appium with XCUITest**: more control and wider language support, but a server, drivers and much more setup for the same flows.
- **Native XCUITest in the Xcode project**: no new tool, but Swift tests for iOS only, and Android would need a separate suite.
- **Mocked backend for the app tests**: hermetic, but needs a way to point the release build at a mock and to fake Supabase sign-in; the review account against production also checks the deployed backend.

## Consequences
- The owner's Mac must be on and the runner service running at night; otherwise the nightly run waits in the queue. It needs Xcode 26+, Node 22, pnpm, Java 21 and Maestro installed once. A job on that runner can reach whatever the runner's macOS user can, so the runner should run as a separate macOS user without the owner's Keychain.
- New test tooling: Maestro (installed with Homebrew locally and with Maestro's installer in CI) and Java 21.
- The tests depend on production and on the review account; if either is down or the password secret is missing, the nightly run fails.
- The recording flow covers the client path: the tap, the recorder state machine, `MediaRecorder` encoding in WKWebView, building the upload blob and showing the transcript. It does not cover the real microphone and the iOS permission prompt (the test build never opens the microphone), the server's handling of the audio, or real speech recognition; those stay a check on a real iPhone.
- The simulator test build differs from the App Store build only by the flag. A store build made after `sim` without `sync` was the risk; `sim` therefore puts the normal build back into `frontend/ios` itself.
- Google and Apple sign-in are not automated.
- Android flows are not added yet; Maestro can run the same flows on an emulator later.
- Maestro writes typed text, the password included, into its debug output. `scripts/test-app.sh` keeps that output in a temporary folder and masks the password before moving it to `artifacts/maestro/`; the workflow does not upload it. Before this was in place, early local runs left unmasked logs in `~/.maestro/tests`; they were deleted.
- The review account is shared with app-store reviewers, and its server-side state persists between runs (interface language, personal topics, statistics). A reviewer who switches the language to English or creates a topic starting with "Банк" can make the flows fail; nightly runs also add sessions to that account's statistics. A separate test account would remove this if it becomes a problem.
- The flows sign in by typing the email, which goes straight to Supabase; the backend's `turktalkreview` alias that reviewers use is not exercised.
